## 2. Family-plan member misclassification (July-2026 thread + related)

**CONFIRMED, ACTIVE in the wild:** "Premium Family Plan does not allow for creating apps for member" (community.spotify.com, Spotify-for-Developers board, td-p/7503003). A family-plan owner created a dev app **on their child's member account** (Raspberry Pi / Home Assistant voice-speaker use case) and got: *"The Spotify API has been changed and Developer applications created with a free account can no longer access the API"* — i.e. **Spotify's premium-entitlement check classified a family-plan MEMBER account as a free account**. The suggested "resolution" was just: create the app on the plan-owner's (true Premium) account. No fix for the member-account classification itself. [COMMUNITY] https://community.spotify.com/t5/Spotify-for-Developers/Premium-Family-Plan-does-not-allow-for-creating-apps-for-member/td-p/7503003

- Related: "Developer account incorrectly marked as Premium-restricted" — accounts flagged Premium-restricted where even new minimal apps fail with "Active premium subscription" required. Shows the premium classification backend has known false negatives. [COMMUNITY] https://community.spotify.com/t5/Spotify-for-Developers/Developer-account-incorrectly-marked-as-Premium-restricted/td-p/7479194
- Related: "Is Spotify premium required for app developer account" td-p/7376724 — confirms Feb-2026 policy: app-registering account must hold active Premium. [COMMUNITY] https://community.spotify.com/t5/Spotify-for-Developers/Is-Spotify-premium-requirefor-app-developer-account-d/td-p/7376724
- Older non-dev threads show family-member accounts sometimes showing as **free in the product itself** — classic cause: member logged into a *different email/account* than the one invited to the plan; resolution was logging in with the invited email. Directly matches "she says her email has no individual Premium" — worth verifying which account she actually OAuth-linked. [COMMUNITY] https://community.spotify.com/t5/Premium-Family/Premium-family-plan-not-working-on-family-member-account/m-p/6352319 and https://community.spotify.com/t5/iOS-iPhone-iPad/Spotify-family-member-not-premium-in-app/td-p/1008946

[INFERRED] If the platform's *app-creation* premium check misclassifies family members as free, the *streaming-entitlement* check used by the Web Playback SDK / `cpapi` may share the same account-classification source — a family member could get `account_error` (or a silent playback denial) despite genuinely having Premium via the plan. No community post yet shows the SDK case specifically, but the classification bug is proven in one enforcement path.

## 3. /v1/me `product` field for dev-mode apps — enforcement in the wild

**CONFIRMED both in docs and in the wild.**

- [DOC] Official Web API Changelog (February 2026): the `/v1/me` user profile response for development-mode apps **lost `country`, `email`, `product`, `explicit_content`, `followers`**. Also mass removals across album/track/artist objects (`available_markets`, `popularity`, `external_ids`, etc.) and several catalog endpoints. https://developer.spotify.com/documentation/web-api/references/changes/february-2026
- [COMMUNITY] rspotify (Rust Spotify lib) issue #550 "Spotify Web API changes (February 2026)": maintainer documented real API responses confirming enforcement — new integrations restricted from **2026-02-11**, existing dev-mode apps migrated **2026-03-09**. Client-credentials metadata calls now fail; model fields including `product` gone. https://github.com/ramsayleung/rspotify/issues/550
- [COMMUNITY] spotDL issue #2617 and TechCrunch coverage corroborate: dev-mode requires Premium owner, ~5 test users, product/metadata field removals. https://github.com/spotDL/spotify-downloader/issues/2617 · https://techcrunch.com/2026/02/06/spotify-changes-developer-mode-api-to-require-premium-accounts-limits-test-users/
- [COMMUNITY] Headphonesty overview of the crackdown fallout: https://www.headphonesty.com/2026/02/spotify-crackdown-thousands-third-party-music-apps/

[INFERRED] Our client ID was created ~June 2026, i.e. AFTER 2026-02-11 — the `product` field has **never** been present in our `/v1/me` responses. Any premium-detection logic reading `me.product` gets `undefined`/missing for **every** user (including the 5 that work), so `product` cannot explain the one silent user — but it also means we have NO server-side way to distinguish her entitlement, and any code branching on `product === 'premium'` is dead or (worse) silently falsy for everyone.

## 5. Client-side verbose diagnostics techniques

- **`cpapi.spotify.com` 404 / "CloudPlaybackClientError: PlayLoad event failed with status 404"**: the SDK POSTs telemetry-ish playback events to `cpapi.spotify.com/v1/client/{...}/event/item_before_load`; a 404 there raises `CloudPlaybackClientError` in console. Community consensus: usually **non-fatal** — music still plays; side-effect is the player's `loading` state not updating. Do NOT treat this console error as the audio failure by itself. [COMMUNITY] https://community.spotify.com/t5/Spotify-for-Developers/event-item-before-load-returning-404/td-p/6769401
- **`404 Device not found` on `PUT /v1/me/player/play?device_id=...`** is different and IS fatal for that attempt: the SDK device wasn't registered (yet) or was reaped. Known race: play issued immediately after `ready` fires can still 404; retry-after-delay is the standard community workaround. [COMMUNITY] https://community.spotify.com/t5/Spotify-for-Developers/Spotify-Web-Playback-SDK-404-device-not-found/td-p/5472057 · https://github.com/spotify/web-api/issues/1325
- **`autoplay_failed` event** exists precisely for silent-no-audio-from-autoplay: *"Web Playback SDK emits a new event when the browser autoplay rules prohibit playback"*; pair with `player.activateElement()` called synchronously inside a user-gesture handler (must be called in advance to survive a transfer with `play:true`). [DOC-adjacent blog + COMMUNITY] https://developer.spotify.com/blog/2021-09-13-web-playback-sdk-out-of-beta · https://community.spotify.com/t5/Spotify-for-Developers/Embedded-player-won-t-autoplay-track/td-p/5616768
- **The five SDK error events carry distinct `message` strings** — `initialization_error` (EME/DRM/widevine failures land here), `authentication_error` (token invalid/expired/missing `streaming` scope), `account_error` ("This functionality is restricted to premium users only." — the premium-entitlement rejection), `playback_error`, plus `autoplay_failed` (no message). Community reports repeatedly show the *distinguishing* information is in the raw message string + accompanying network responses (status + body of `/v1/me`, `/v1/me/player/*`, cpapi calls), not in which callback fired. A diagnostic layer should log: every error event verbatim, every Web API response status AND body, `getOAuthToken` invocations (the SDK calls it lazily; a callback that never calls `cb(token)` hangs the SDK silently — a classic pitfall), and `player.connect()`'s resolved boolean. [COMMUNITY] (threads above; getOAuthToken pitfall: widely reported in getting-started discussions)
- No documented official "debug flag" for the SDK was found; the practical technique is intercepting console + network (the SDK's iframe talks to `cpapi.spotify.com` and a `dealer.spotify.com` websocket; watching those two hosts in DevTools Network is the community-standard deep-diagnosis method). [COMMUNITY/INFERRED]

## Implications for our code

1. **`rollplay/app/audio_management/hooks/useSpotifyPlayback.js:452`** — `if (data.profile?.product !== 'premium') { setStatus('not_premium'); return; }` is the prime suspect gate. [DOC] Feb-2026 removed `product` from dev-mode `/v1/me` (our app, created ~June 2026, was born under this regime). Since 5/6 users pass this gate, our app evidently still receives `product` (enforcement is demonstrably inconsistent in the wild) — meaning for the silent user it may return `"free"`/absent via the family-member misclassification (section 2/3b), silently blocking SDK creation before ANY SDK error listener exists. The diagnostic layer MUST log the raw profile JSON her browser receives.
2. **`api-site/integrations/spotify/endpoints.py:182-189`** — any `httpx.HTTPStatusError` from `/v1/me` (including the allowlist 403 whose body literally says "User not registered in the Developer Dashboard") is swallowed into `connected: False`. Three distinct root causes (revoked token, allowlist mismatch, geo/premium 403) collapse into the frontend's 'not_connected'. Log `e.response.status_code` AND `e.response.text` — the body string is the only thing that distinguishes them (section 4).
3. **`useSpotifyPlayback.js:531-534`** — `initialization_error` and `authentication_error` both map to status 'error', and `account_error` maps to 'not_premium' (same status as the line-452 gate), so downstream we cannot tell profile-gate rejection from SDK entitlement rejection. Diagnostic layer: log each event's verbatim `message` and keep the originating event name in state.
4. **Allowlist audit (no code)** — verify in the dashboard that her entry's email EXACTLY matches her Spotify account's registered email (Facebook/Google-login and alias emails are the classic silent mismatch, section 4). Also count entries: post-Feb-2026 dev-mode apps are reported capped at 5 test users (endpoint51/TechCrunch) — we have 6 users; if the cap applies to our app, the last-added user may be the broken one. Check who was added 6th.
5. **`useSpotifyPlayback.js` play-call path** — when diagnosing her session, distinguish `cpapi.spotify.com` PlayLoad 404s (non-fatal, ignore) from `PUT /me/player/play` 404 Device-not-found (fatal race on fresh device ids; retry with delay) (section 5).
6. **Ask her to re-do the OAuth link while logged into the exact invited-to-the-plan account** — multiple family threads resolved as "member was signed into a different account/email than the one on the plan" (section 2/3b). The raw `/v1/me` `id`/`display_name` we already store (endpoints.py `_map_profile`) can confirm WHICH Spotify account she actually linked.
